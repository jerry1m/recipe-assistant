## 1. LLM / 模型加载

### Q1.1 每个 Agent 都加载一次模型，显存爆炸 🔥

**问题描述**：每个 Agent（Router、TextRAG、NutritionSQL 等）各自从 HuggingFace 加载 Qwen2.5-0.5B-Instruct，导致显存重复占用。首个 Agent 加载耗时 ~43s，后续 Agent 又各自加载 ~1.5GB 显存，直接 OOM。

**根因**：无共享模型实例，每个 Agent 独立初始化 pipeline。

**解决方案**：实现线程安全的**全局单例**。

```python
# src/core/utils/llm.py
_model = None
_tokenizer = None
_model_lock = asyncio.Lock()

def _load_model():
    """全局单例，仅加载一次"""
    global _model, _tokenizer
    if _model is not None:
        return _model, _tokenizer
    # ... 加载模型
```

- 首调加载 ~43s / ~1.5GB 显存
- 后续调用 ~1.5-2s（复用 pipeline）
- 所有 Agent 通过 `generate()` 共享同一实例

**涉及文件**：`src/core/utils/llm.py`

---

### Q1.2 模型生成阻塞事件循环 ⏳

**问题描述**：LLM 的 `generate()` 是同步阻塞调用，在 FastAPI 异步接口中会导致事件循环卡死，整个 API 无法响应其他请求。

**根因**：Transformers 的 `model.generate()` 是 CPU/GPU 密集型同步操作，直接 `await` 不会释放事件循环。

**解决方案**：使用 `asyncio.to_thread()` 将同步调用抛到线程池执行。

```python
async def generate(query, context, ...):
    # 异步中执行同步阻塞调用
    result = await asyncio.to_thread(_api_generate_sync, ...)
    if result is not None:
        return result
    async with _model_lock:
        return await asyncio.to_thread(_generate_sync, ...)
```

**同理用于**：
- `generate_with_tools()` — Function Calling 调用
- `translate_query()` — query 翻译

**涉及文件**：`src/core/utils/llm.py`

---

### Q1.3 API 调用超时后自动回退效果差

**问题描述**：当 ModelScope API 超时（默认 30s 无响应），代码等待超时才回退到本地模型，用户感知到 ~30s 的空白等待。

**根因**：API 客户端超时设置过长，且没有快速失败机制。

**解决方案**：缩短 API 超时 + 增加重试 + 快速回退。

```python
_API_TIMEOUT = 10.0  # 从 30s 缩短到 10s
# API 调用失败后立即回退本地模型
```

**实际效果**：即使 API 挂了，本地模型 1.5s 内回退完成，用户无感。

**涉及文件**：`src/core/utils/llm.py`

---

### Q1.4 本地模型加载路径硬编码

**问题描述**：在服务器上部署时，模型权重不在默认的 HuggingFace 缓存路径，启动报错 `OSError: Can't load model`。

**根因**：`from_pretrained()` 默认从 HF 缓存加载，未指定本地路径。

**解决方案**：通过 `MODEL_PATH` 环境变量指定本地路径，并优先使用本地缓存。

```python
import os
model_path = os.environ.get("MODEL_PATH", "Qwen/Qwen2.5-0.5B-Instruct")
_tokenizer = AutoTokenizer.from_pretrained(model_path, trust_remote_code=True)
_model = AutoModelForCausalLM.from_pretrained(model_path, ...)
```

**涉及文件**：`src/core/utils/llm.py`

## 2. 检索与向量索引

### Q2.1 BM25 + FAISS 分数不可比，无法直接融合

**问题描述**：BM25 返回的是 TF-IDF 加权分数（0~50+），FAISS 返回的是余弦相似度（-1~1），直接加权融合需要调权重且不稳定。

**根因**：异构检索系统的分数分布不同，不具备可比性。

**解决方案**：使用 **Reciprocal Rank Fusion（RRF）**，不看分数只看排名。

```python
# RRF 融合: 排名倒数求和的倒数
k = 60
rrf_score = sum(1 / (k + rank) for rank in [bm25_rank, faiss_rank])
```

RRF 的优点是：
- 不依赖分数量纲，对异构检索系统鲁棒
- 常数 K=60 是经验值，对大多数场景适用
- 实现简单，无需训练

**涉及文件**：`src/core/retrievers/hybrid.py`

---

### Q2.2 中文 query 检索英文语料效果差

**问题描述**：用户中文 query（如"红烧肉怎么做"）直接检索英文食谱（Recipe1M），BM25 分词和 FAISS 语义匹配效果都很差。

**根因**：语料是英文的，中文 query 和英文文档在字符层面不匹配。

**解决方案**：检索前用 LLM 将中文 query 翻译为英文。

```python
# 中文 → 英文翻译后检索
async def translate_query(query: str) -> str:
    if not _contains_chinese(query):
        return query
    # 调用 LLM 翻译
    return await generate(query, system_prompt="Translate to English:")  ```

**同时**：
- BM25 使用 **jieba 中文分词**处理中文，whitespace split 处理英文
- LLM 生成回答时仍用原始中文 query，保证输出中文
- `_DEFAULT_SYSTEM_PROMPT` 明确要求 `Answer in the same language as the user's question`

**涉及文件**：`src/core/retrievers/hybrid.py`、`src/core/utils/llm.py`

---

### Q2.3 步骤碎片化导致 LLM 无法理解完整流程

**问题描述**：某菜谱有 5 个步骤，按单条切分后，检索可能只返回"Step 3: Bake for 20 minutes"，LLM 拿到这碎片信息无法给出完整回答。

**根因**：Chunk 过于细粒度，丢失了上下文连贯性。

**解决方法**：步骤不按单条切分，全部步骤合并为一个 chunk。

```python
# 步骤全量合并: "Step 1. ...\nStep 2. ...\n..."
steps_text = "\n".join(
    f"Step {s.step_number}: {s.content}" for s in sorted(recipe.steps, key=lambda x: x.step_number)
)
```

**涉及文件**：`scripts/ingest_real_data.py`（chunk 构建逻辑）

---

### Q2.4 CLIP 检索默认占用 cuda:0，抢占其他进程 GPU

**问题描述**：CLIP 图文检索默认加载到 `cuda:0`，如果其他进程（如本地 LLM 推理）正在占用，会导致显存不足或 CUDA OOM。

**根因**：`CLIPModel.from_pretrained().to("cuda")` 默认选第一块 GPU。

**解决方案**：自动检测空闲 GPU。

```python
@staticmethod
def _pick_device() -> str:
    """nvidia-smi 解析空闲显存，≥3GB 才用 CUDA，否则 CPU"""
    result = subprocess.run(
        ["nvidia-smi", "--query-gpu=index,memory.free", "--format=csv,noheader,nounits"],
        capture_output=True, text=True, timeout=5,
    )
    for line in result.stdout.strip().split("\n"):
        parts = line.split(", ")
        idx, free_mib = int(parts[0]), int(parts[1])
        if free_mib >= 3000:  # CLIP 推理 peak ~1.5GB，留 2 倍余量
            return f"cuda:{idx}"
    return "cpu"
```

**涉及文件**：`src/core/retrievers/clip_retriever.py`

## 3. 数据与分块策略

### Q3.1 Recipe1M 数据量大，首次加载慢

**问题描述**：Recipe1M 完整数据集 ~1M 条食谱，首次 `load_dataset` 下载 + 解析需要数十分钟。

**根因**：全量下载，未使用流式加载。

ds = load_dataset("Eitanli/cuisine_type", split="train", streaming=True)
for i, example in enumerate(ds):
    if i >= 5000:
        break

```

**同时**：设置 `HF_ENDPOINT=https://hf-mirror.com` 使用镜像站加速国内下载。

**涉及文件**：`scripts/ingest_real_data.py`

---

### Q3.2 原始数据纯文本非结构化

**问题描述**：Recipe1M 原始数据是纯文本格式，recipe 字段包含标题、食材、步骤混在一起，无法直接用于结构化查询（如 SQL 营养查询）。

**根本原因**：数据源未做结构化处理。

**解决**：编写解析器将纯文本拆分为结构化字段。

```python
def parse_raw_recipe(text: str) -> dict:
    lines = text.strip().split("\n")
    title = lines[0]
    ingredients = []
    steps = []
    in_ingredients = True
    for line in lines[1:]:
        if line.startswith("Instructions:") or line.startswith("Directions:"):
            in_ingredients = False
            continue
        if in_ingredients:
            ingredients.append(parse_ingredient(line))
        else:
            steps.append(line)
    return {"title": title, "ingredients": ingredients, "steps": steps}
```

**涉及文件**：`scripts/ingest_real_data.py`

## 4. 意图识别 (Router)

### Q4.1 Function Calling 偶尔返回错误 JSON

**问题描述**：Qwen3.5-35B 的 Function Calling 偶尔返回 JSON 格式错误（缺少括号、字段名错误），导致 `json.loads()` 失败。

**根因**：LLM 生成不稳定，小概率出现格式偏差。

**解决方案**：添加 try-catch 兜底 + 规则降级。

```python
try:
    result = json.loads(tool_call.function.arguments)
except (json.JSONDecodeError, KeyError, TypeError):
    # 格式错误时走规则兜底
    return RouterResult(intent=IntentType.CHITCHAT, confidence=0.7, slots={})
```

**涉及文件**：`src/agents/router.py`

---

### Q4.2 "热量"等明确关键词走了 Function Calling 慢路径

**问题描述**：用户输入"热量多少"这种非常明确的营养查询，原本可以直接匹配，却走了 Function Calling 路径（~2s 延迟）。

**根因**：没有规则快速通道，所有请求都经过 LLM 分类。

**解决方案**：在 Function Calling 前加**规则快速通道**。

```python
# 规则快速通道：常见关键词直接匹配
_RULE_PATTERNS = [
    (re.compile(r"(热量|卡路里|低卡|calorie)"), IntentType.NUTRITION_FILTER, 0.95),
    (re.compile(r"(怎么做|步骤|如何做)"), IntentType.STEP_QA, 0.92),
    # ... 更多模式
]

def _rule_classify(query: str) -> RouterResult | None:
    for pattern, intent, confidence in _RULE_PATTERNS:
        if pattern.search(query):
            slots = _extract_slots(query, intent)
            return RouterResult(intent=intent, confidence=confidence, slots=slots)
    return None
```

**规则快速通道延迟：0ms，Function Calling 延迟：~2s**

**涉及文件**：`src/agents/router.py`

## 5. Agent 执行与编排

### Q5.1 Fault Tolerance 并行导致不必要的兜底延迟

**问题描述**：NutritionSQL 的 Worker 很快（~12ms），但 Fallback 检索很慢（~20s），`asyncio.gather(worker, fallback)` 要等最慢的任务完成才返回。

**根因**：All Agents 统一使用 `asyncio.gather` 并行 Worker 和 Fallback。

**解决方案**：Worker 成功后直接返回，不等 Fallback。

```python
if intent == IntentType.NUTRITION_FILTER.value:
    worker_result_model = await agent.run(query=query, slots=state.get("slots", {}))
    if worker_result_model.success:
        return result_data  # 直接返回，不等 Fallback
    # Worker 失败时才跑 Fallback
    fb_draft, fb_chunks = await _prepare_text_fallback(query)
```

**同一修复也应用于 SubstitutionAgent**。

**涉及文件**：`src/orchestrator/graph.py`

---

### Q5.2 LangGraph State 类型安全问题

**问题描述**：LangGraph 的 State 用 `TypedDict` 定义，但运行时并不强制类型检查，某个节点返回了 None 或类型不匹配的字段，导致下游节点 AttributeError。

**根因**：Python TypedDict 仅用于类型提示，无运行时校验。

**解决方案**：每个节点函数用默认值兜底。

```python
async def some_node(state: RecipePipelineState) -> dict:
    safe_val = state.get("some_field", default_value)
    return {"result": safe_val}
```

**涉及文件**：`src/orchestrator/graph.py`

## 6. SQL 查询

### Q6.1 NutritionSQL 延迟高达 113s 🔥

> 这是整个项目中影响最大的性能问题。

**现象**：每次查询"美国美食低热量"等营养问题，耗时 113 秒。

**根因分析**：

```
原因链:
1. Router 命中 nutrition_filter，但没有提取 cuisine_type
2. NutritionSQL 走 LLM 翻译 SQL → API 调用超时 (30s)
3. 自动回退到本地 Qwen2.5-0.5B (~30s/次)
4. Critic 检查免责声明发现缺失 → 拒绝 → 重试 (2次 × 30s)
5. Formatter 再次添加免责声明 → 最终输出双免责声明
总计: 30s(API超时) + 30s(本地) + 30s(Critic重试1) + 30s(Critic重试2) - 重叠 ≈ 113s
```

**解决方案**：多管齐下。

| 问题 | 修复 | 效果 |
|------|------|------|
| LLM 翻译 SQL 太慢 | 5 个关键词 SQL 模板（0 LLM 延迟） | 12ms |
| 免责声明重复 | Formatter 统一添加，Critic 跳过 | 重试 0 次 |
| 菜系不匹配 | Router 提取 cuisine_type，注入 SQL | 正确过滤 |
| 并行 Fallback 阻塞 | 先跑 Worker，成功即返回 | 不阻塞 |

**最终结果**：**113s → 12ms**，优化约 9400 倍。

**涉及文件**：`src/agents/nutrition_sql.py`、`src/agents/critic.py`、`src/agents/formatter.py`、`src/agents/router.py`

## 7. 质量检测 (Critic)

### Q7.1 双免责声明导致 Critic 重试循环

**问题描述**：Answer 中出现"⚠️ 营养建议仅供参考..."两条相同的免责声明。而且 Critic 检查免责声明发现"缺失"→拒绝→重试，浪费 ~40s。

**根因**：

```
营养查询流程:
  NutritionSQL → "XX 食物营养丰富" (无免责)
  Critic → 检查发现无免责 → 拒绝 → 重试
  重试的 NutritionSQL 内置了免责 → "XX 食物... ⚠️ 仅供参考"
  Formatter → 又加一条 → "XX 食物... ⚠️ 仅供参考 ⚠️ 仅供参考"
```

**解决方案**：

1. **移除所有 Agent 内置免责声明**
2. **在 Critic 中增加 `need_disclaimer` 标志**：为 `True` 时跳过免责检查
3. **Formatter 作为免责声明唯一添加点**

```python
# Formatter 统一添加
if need_disclaimer:
    draft += "\n\n⚠️ 营养建议仅供参考，具体请以专业营养师意见为准。"
```

```
最终规范:
Agent (无免责) → Critic (need_disclaimer=True 时跳过) → Formatter (统一添加)
```

**涉及文件**：`src/agents/critic.py`、`src/agents/formatter.py`

---

### Q7.2 Critic 重试 2 次后仍失败，回答质量下降

**问题描述**：Critic 连续拒绝 2 次后，系统走兜底（纯检索拼接），回答质量明显低于 LLM 生成。

**根因**：达到最大重试次数后直接放行或走兜底，没有中间状态。

**解决方案**：重试 2 次后仍失败时走预计算兜底，保留检索片段中的有用信息，至少保证回答有事实依据。

**涉及文件**：`src/orchestrator/graph.py`（`after_critic` 条件边）

## 8. 多轮对话与记忆管理

### Q8.1 process 内存储会话重启丢失

**问题描述**：使用 `dict` 存储 `ConversationMemory`，服务重启后所有对话历史丢失，用户需要重新开始。

**根因**：无持久化存储。

**解决方案**：引入 Redis 持久化。

```python
# Redis Key 结构
recipe:session:{id}         → Hash(session_id, created_at, last_active)
recipe:session:{id}:turns   → List(TurnRecord JSON)
recipe:session:{id}:summary → String (LLM 压缩摘要)
recipe:session:{id}:meta    → Hash(compressed_count)

# Redis TTL 自动管理过期（86400s），不需要手动清理
```

**同时保留内存兜底**：Redis 不可用时自动降级到 `_fallback_store` dict。

**涉及文件**：`src/core/memory.py`

---

### Q8.2 Context 过长撑爆 LLM

**问题描述**：多轮对话超过 5 轮后，`conversation_context` 超过 4000 tokens，Router 的 LLM 调用超时或过载。

**根因**：无上下文长度控制。

**解决方案**：Token 感知的滑动窗口。

```python
async def get_context(self, max_tokens=2048) -> str:
    """从最新轮次往前保留，超出预算截断"""
    lines = []
    token_count = 0
    for t in reversed(turns):
        text = f"用户: {t.query}\n意图: {t.intent}\n助手: {t.answer}"
        tokens = _estimate_tokens(text)
        if token_count + tokens > max_tokens and kept_count > 0:
            break
        lines.insert(0, text)
        token_count += tokens
    return "\n".join(lines)
```

**涉及文件**：`src/core/memory.py`

---

### Q8.3 LLM 压缩异步任务在进程退出时丢失

**问题描述**：`asyncio.create_task(memory.compress_if_needed())` 在后台运行，如果主请求已经返回且进程退出，压缩任务被丢弃。

**根因**：asyncio 未完成任务在事件循环关闭时被取消。

**解决方案**：不要求强一致性——压缩不是关键路径，即使丢失也不影响主流程。下次请求时重新压缩即可。

```python
# save_memory_node — 不 await，不阻塞响应
asyncio.create_task(memory.compress_if_needed())
```

**涉及文件**：`src/orchestrator/graph.py`、`src/core/memory.py`

## 9. API 与部署

### Q9.1 大模型首次请求超时（~43s）

**问题描述**：服务启动后第一个请求需要 ~43s，因为需要从 HuggingFace 下载并加载 Qwen2.5-0.5B。

**根因**：模型懒加载 + 首次下载权重。

**解决方案**：使用全局单例 + 健康检查触发预热。

```python
# health check 时触发模型加载
@app.get("/health")
async def health():
    # 触发本地模型预热
    from src.core.utils.llm import _load_model
    _load_model()  # 仅在当前进程首次调用时真正加载
    return {"status": "healthy"}
```

**实际效果**：首请求 ~43s → Health check 预热后的首请求 ~1.5s。

### Q9.2 FastAPI SSE 流式输出与 LangGraph 集成

**问题描述**：LangGraph 执行完成后返回完整结果，无法中间流式输出 token。

**根因**：LangGraph 是 request-response 模式，不支持逐 token 流式。

**解决方案**：在 `supervisor.py` 中判断 `stream=True` 时使用 SSE。

```python
# src/api/streaming.py
async def stream_response(request, orchestrator):
    async def event_stream():
        # 先执行 LangGraph 获取完整结果
        response = await orchestrator.ask(request)
        # 然后逐字 SSE 输出
        for char in response.answer:
            yield f"data: {json.dumps({'token': char})}\n\n"
        yield f"data: {json.dumps({'event': 'done'})}\n\n"
    return StreamingResponse(event_stream(), media_type="text/event-stream")
```

> 注意：这是简化方案。更理想的方案是修改 LangGraph 支持 callback 流式输出，但当前方案已经能满足用户体验需求。

**涉及文件**：`src/api/streaming.py`

### Q10.2 检索质量评估标准难定义

**问题描述**：检索返回的 chunks 是否相关难以量化判断，因为同一 query 可以有多个合理答案。

**根因**：信息检索评估天然具有主观性。

**解决思路**：使用 MRR（Mean Reciprocal Rank）和 Recall@K 等标准 IR 指标，判断期望的 chunk 是否出现在检索结果中。

```python
def mean_reciprocal_rank(retrieved: list[str], expected: list[str]) -> float:
    """期望文档在检索结果中的排名倒数"""
    for i, doc in enumerate(retrieved):
        if doc in expected:
            return 1.0 / (i + 1)
    return 0.0

def recall_at_k(retrieved: list[str], expected: list[str], k: int) -> float:
    """Top-K 中的召回率"""
    hits = sum(1 for doc in retrieved[:k] if doc in expected)
    return hits / len(expected) if expected else 0.0
```

**涉及文件**：`src/eval/metrics.py`

## 11. 新组件集成（从 travel-agent-guide 移植）

> 从 travel-agent-guide 移植 5 个关键设计：Circuit Breaker、LongTermMemory、ToolRegistry、Planner Agent、Reflection Agent。

### Q11.1 API 调用连续失败时无快速失败机制

**问题描述**：API 调用超时或网络异常时，每次都要等待超时（~30s）才会回退本地模型。连续失败场景下，每次请求都浪费 30s。

**根因**：无熔断保护，每次请求都"试了再说"。

**解决方案**：移植异步三态 Circuit Breaker。

```python
# src/core/utils/circuit_breaker.py
class AsyncCircuitBreaker:
    def __init__(self, failure_threshold=3, recovery_timeout=30):
        self.state = CircuitBreakerState.CLOSED
        self.failure_count = 0
        self.failure_threshold = failure_threshold
        self.recovery_timeout = recovery_timeout      # 首轮 30s
        self.max_recovery_timeout = 60                 # 最大 60s

    async def check(self) -> bool:
        if self.state == CircuitBreakerState.OPEN:
            if time.time() - self.last_failure_time >= self.recovery_timeout:
                self.state = CircuitBreakerState.HALF_OPEN
                return True  # 放行探测
            return False     # 快速失败

    async def record_failure(self):
        self.failure_count += 1
        self.total_failure_count += 1
        if self.failure_count >= self.failure_threshold:
            self.state = CircuitBreakerState.OPEN
            self.recovery_timeout = min(self.recovery_timeout * 2, self.max_recovery_timeout)
```

**集成**：`llm.py` 的 `_api_generate_sync()` 调用前后分别 `check()` 和 `record_success/failure()`。

**效果**：3 次连续失败后 → OPEN → 后续请求 0ms 直接走本地回退。

### Q11.2 跨会话用户偏好缺失，每次都是"陌生人"

**问题描述**：ConversationMemory 只保存单次会话内的对话历史，用户下次再来时系统不知道他是否素食、对什么过敏。

**根因**：无长效跨会话记忆机制。

**解决方案**：移植 LongTermMemory，JSON 文件持久化。

```python
# src/core/long_term_memory.py
class LongTermMemory:
    def __init__(self, storage_dir="data/long_term_memory"):
        self.storage_dir = Path(storage_dir)
        self.storage_dir.mkdir(parents=True, exist_ok=True)
        self._cache: dict[str, dict] = {}      # 内存缓存, 减少 IO
        self._lock = asyncio.Lock()

    async def load(self, user_id: str) -> dict:
        if user_id not in self._cache:
            file_path = self.storage_dir / f"{user_id}.json"
            if file_path.exists():
                data = json.loads(file_path.read_text())
                self._cache[user_id] = data
        return self._cache.get(user_id, {})
```

**集成**：`graph.py` 中 `load_memory_node` 后调用 `LongTermMemory.load(user_id)`，`save_memory_node` 后调用 `save()`。

### Q11.3 Planner 需要动态工具发现，硬编码调用链扩展性差

**问题描述**：Planner Agent 需要根据 LLM 生成的计划动态调用不同工具（检索食谱、查营养、查替换等），但原有 Worker 是固定 intent → 固定 Agent 的硬编码。

**根因**：无统一的工具注册和发现机制。

**解决方案**：移植 ToolRegistry，支持 MCP 兼容目录和自动发现。

```python
# src/core/tools/registry.py
class ToolRegistry:
    _tools: dict[str, RegisteredTool] = {}

    def discover_package(self, package_path: str):
        """扫描包内 register_* 函数自动注册"""
        pkg = importlib.import_module(package_path)
        for name in dir(pkg):
            if name.startswith("register_"):
                getattr(pkg, name)(self)

    async def invoke(self, name: str, **kwargs) -> Any:
        tool = self._tools[name]
        if asyncio.iscoroutinefunction(tool.func):
            return await tool.func(**kwargs)
        return await asyncio.to_thread(tool.func, **kwargs)
```

**注册的工具**：`search_recipes`（混合检索）、`search_nutrition`（营养查询）、`search_substitution`（食材替代）。

**集成**：Planner Agent 的 `_execute_step()` 通过 `get_tool_registry().invoke(tool_name, **kwargs)` 调用。

### Q11.4 快慢车道意图冲突时无显式合并策略

**问题描述**：规则快速通道和 Function Calling 慢通道在结果不一致时，原来直接取 FC 结果，忽略了规则通道可能更准的场景。

**根因**：无显式冲突解决策略。

**解决方案**：移植 travel-agent-guide 的 4 态合并策略。

```python
# src/agents/router.py
def _merge_results(self, rule_result, fc_result):
    if rule_result.confidence >= 0.9:
        return rule_result, "fast_lane_only"
    if rule_result.intent == fc_result.intent:
        return rule_result.with_boost(0.1), "agree"
    # conflict
    if rule_result.confidence > fc_result.confidence:
        return rule_result, "conflict_prefer_rule"
    return fc_result, "conflict_prefer_fc"
```

**效果**：高频关键词（'热量'、'低卡'）规则通道直接命中（0ms），复杂语义走 FC（~2s），冲突时有明确优先级。
