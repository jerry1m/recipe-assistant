## 1. 项目一句话介绍

> **"一个基于 Multi-Agent 架构的智能食谱问答系统，通过 10 个协同 Agent（含 Planner 规划 + Reflection 深度质检）提供食谱推荐、营养查询、食材替换等专业服务，搭载 35B 大模型 API 和 0.5B 本地模型双重保障，LangGraph 编排多轮对话与自动重试。"**

### 备选版本

- **偏工程**："一个实践 Multi-Agent 编排（LangGraph）、混合检索（BM25+FAISS+Rerank）和 LLM 工程化（API+本地双活+Circuit Breaker 熔断）的个人项目，覆盖 5000 条真实食谱的多轮问答。"
- **偏算法**："一个结合 Function Calling 意图识别（快慢车道 4 态合并）、CLIP 图文检索和检索增强生成（RAG）的智能食谱助手，支持 7 类意图的精准路由和 Planner 复杂请求分解执行。"

## 2. 两分钟项目概述

### 2.1 项目背景

"这是我自己设计开发的 Multi-Agent RAG 系统。起因是想做一个真正能用的食谱问答工具，同时实践 Multi-Agent 编排、LLM 工程化、混合检索这些工业级技术。数据来自 Recipe1M 公开数据集，选了 5000 条多菜系英文食谱。"

### 2.2 系统架构（手势引导）

"整体架构分三层：

**第一层 — API 入口层**：FastAPI 提供 REST 和 SSE 流式接口。支持文本问答、图片上传、PDF 文件解析。新增 Circuit Breaker 和 LongTermMemory 监控端点。

**第二层 — 编排层**：用 **LangGraph StateGraph** 构建 12 节点的有向图。核心流程是 `init → 加载记忆(含长效记忆) → 意图识别(快慢车道4态合并) → [Planner 分解执行] → Worker 执行 → Critic 质检 → Reflection 深度质检 → 保存记忆(含长效记忆) → 格式化输出`。Critic 不通过时自动回边重试，最多 2 次。新增 Planner 节点处理复杂请求，Reflection 节点做 LLM 驱动的深度质量检测。

**第三层 — Agent 层**：10 个 Agent 各司其职。Router 用 **Function Calling** 做 7 类意图分类+槽位提取（快慢车道 4 态合并），Planner 做复杂请求分解执行，Reflection 做 LLM 深度质检，TextRAG 做检索增强问答，NutritionSQL 用三路策略查营养，CLIP 做以图搜菜名，还有 PDF 解析、食材替换、Critic 质检和 Formatter 格式化。"

### 2.3 核心技术亮点

"这个项目有几个让我比较自豪的点：

第一是 **容错设计**。LLM 调用优先走 ModelScope API 的 Qwen3.5-35B，前面有 **Circuit Breaker 熔断器** 保护——连续 3 次失败直接熔断，30s 后自动探测恢复。熔断时直接走本地 Qwen2.5-0.5B 回退。如果本地模型也挂了，还有纯检索的兜底，保证服务不中断。所有模型都是全局单例，只加载一次。

第二是 **延迟优化**。营养查询最初要 113 秒，因为我发现每次都要 LLM 翻译 SQL。后来加了 5 个关键词 SQL 模板，常见模式直接匹配预编译 SQL，延迟从 113 秒降到了 12 毫秒，优化了接近一万倍。

第三是 **多轮对话的记忆管理**。用 Redis 持久化会话，Token 感知的滑动窗口控制上下文长度，还实现了 LLM 对话压缩——把旧轮次异步压缩成摘要，压缩率能达到 90%。"

## 3. 分模块深度解析

### 3.1 意图识别（Router）

**面试官问：你们的 Router 怎么做的？**

"我们用了 **三阶段混合策略**：

1. **规则快速通道（0ms）**：用正则匹配常见关键词，比如'热量'直接命中 `nutrition_filter`，置信度设 0.95 直接返回。
2. **Function Calling（~2s）**：定义 7 个 OpenAPI Function，每个 function 对应一个 intent，parameters 就是槽位。比如 `nutrition_filter` 的 parameters 包含 `food`、`nutrient`、`cuisine_type`。Qwen3.5-35B 的语义理解能力很强，能处理'有个美国朋友来做客，做什么给他吃'这种复杂表达，正确识别为 `ingredient_recommend` + `cuisine_type: American`。
3. **规则兜底（中等置信度 0.7）**：FC 失败时的安全网。"

**为什么不直接用 LLM 分类？**

"Function Calling 的优势在于 **意图识别和槽位提取一次完成**，parameters 天然结构化，不需要额外解析。如果用纯 LLM 分类，还需要再用正则或 LLM 提取槽位，增加延迟和出错可能。而且 FC 的延迟可以接受——2 秒左右，相对于整体 3-5 秒的响应来说占比不大。"

### 3.2 混合检索（HybridRetriever）

**面试官问：为什么同时用 BM25 和 FAISS？**

"我们的数据是 5000 条食谱、15000 个 chunk，**单一检索方式有盲区**：

- **BM25 擅长关键词精确匹配**：用户说'红烧肉'，BM25 能精确命中菜名中包含红烧肉的食谱。
- **FAISS 擅长语义匹配**：用户说'想给美国朋友做菜'，FAISS 能匹配到 American 菜系的食谱。
- **BGE-Reranker 做最终精排**：前两路用 RRF（Reciprocal Rank Fusion）融合后，再用 CrossEncoder 精排 Top-K。

RRF 的好处是不依赖分数量纲，两个异构检索系统的分数尺度差异不影响排序。"

### 3.3 LangGraph 编排

**面试官问：为什么选 LangGraph？**

"选择 LangGraph 有几个考虑：

1. **有向图天然适合多步编排**：从 init 到 formatter 的自然流程，用 add_node/add_edge 清晰表达。
2. **条件边支持意图派发**：`route_by_intent` 根据 intent 字段决定走 worker 还是 chitchat_direct。
3. **回边（back edge）支持重试循环**：Critic 不通过时走 revision 节点，再回 worker 重新生成，这是普通 DAG 做不到的。

跟用 LangChain 的 Chain 对比，Graph 更灵活。跟手写状态机对比，LangGraph 提供了 StateGraph 和 TypedDict 状态定义，类型安全，调试方便。"

### 3.4 LLM 对话压缩

**面试官问：多轮对话怎么控制 Token 预算？**

"我实现了两个层面的控制：

**第一层 — Token 感知滑动窗口**：`get_context(max_tokens=2048)` 从最新轮次往回计算，累加到 2048 token 为止，超出部分截断。这样保证每次 Router 收到的上下文不会撑爆 LLM 的 context window。

**第二层 — LLM 异步压缩**：`save_memory_node` 保存对话后，用 `asyncio.create_task(memory.compress_if_needed())` 在后台启动压缩。把超出窗口的旧轮次调用 LLM 压缩为 1-3 句摘要，合并到已有摘要中。下次请求时，Router 看到的是'摘要 + 最新几轮完整对话'。

实测 9 轮对话，压缩前 431 tokens，压缩后 42 tokens，压缩率 9.7%，节省了 90% 以上的 token。"

## 4. 常见面试追问与回答

### Q1: 如果并发 1000 个请求，你的系统能撑住吗？

"当前架构是单机部署，1000 并发会有几个瓶颈：

- **LLM API 调用**：Qwen3.5-35B API 本身支持高并发，但本地回退的 Qwen2.5-0.5B 是单例串行执行的（有 `_model_lock`），高并发时本地回退会排队。
- **Redis 连接池**：当前是单连接，理论上可支持数千 QPS。
- **FAISS 检索**：15000x384 的索引检索是毫秒级的，不是瓶颈。

如果要支撑高并发，可以：① 加 API 调用并发控制（信号量限流） ② 本地 LLM 用 vLLM 部署支持多并发 ③ 加缓存层减少重复查询。"

### Q2: 为什么选 Qwen3.5-35B，不用 GPT-4 或本地 LLaMA？

"选择 ModelScope API 的 Qwen3.5-35B 主要考虑：

1. **国内可访问**：不需要翻墙，延迟低且稳定。
2. **35B 参数性价比高**：效果接近 GPT-3.5 水平，成本很低（甚至免费额度足够用）。
3. **兼容 OpenAI 格式**：可以无缝切换到其他 API，通过 .env 配置即可。

本地 Qwen2.5-0.5B 是我用来做兜底的——它只占 1.5GB 显存，加载快，虽然效果不如 35B，但至少保证服务不中断。"

### Q3: 怎么做的事实核查（Critic）？

"Critic 目前做三个维度的检查：

1. **完整性**：回答不能为空。
2. **合规**：营养和替换建议需要免责声明。但有个坑——如果 Agent 和 Formatter 都加免责声明，Critic 会因为看到一句话里有免责而通过，最终输出两条。我们的方案是 **Formatter 统一添加**，`need_disclaimer=True` 时 Critic 跳过免责检查。
3. **TODO — 幻觉检测**：目前还没做完全，计划用 LLM 检查答案中的引用是否在 provenance 中能找到对应内容。

如果 Critic 不通过且 retry_count < 2，走 revision 节点回 worker 重新生成，并把 Critic 的 `suggestions` 作为 `feedback` 传入。"

### Q4: RRF 融合的原理是什么？为什么不用加权融合？

"RRF（Reciprocal Rank Fusion）的公式是：

$$RRF(doc) = \sum_{retriever \in R} \frac{1}{k + rank_{retriever}(doc)}$$

K 是常数，设为 60。

**加权融合的问题**：BM25 的分数和 FAISS 的余弦相似度不在同一个量纲上，加权融合需要调权重且不稳定。RRF 只看排名不看分数，分数差异不影响排序，更鲁棒。"

### Q5: 三路 SQL 策略的具体实现？

"**第一路 — 关键词 SQL 模板**：定义 5 个正则模式（低热量/高蛋白/低脂/低碳水/通用），命中后直接注入预编译 SQL。0 LLM 延迟，12ms 返回。

**第二路 — LLM 翻译 SQL**：复杂查询走 LLM 翻译，system prompt 包含表结构和规则，用 few-shot 示例引导。生成的 SQL 经过 sqlglot AST 校验（仅允许 SELECT、表名白名单），然后在 SQLSandbox 中只读执行。

**第三路 — 混合检索兜底**：前两路都失败时，回到 HybridRetriever 做检索 + LLM 生成回答。"

### Q6: 中文 Query 怎么处理的？

"三个处理点：

1. **BM25 分词**：用 `_CJK_RE` 正则检测是否含中文字符，是则用 jieba 分词，否则 whitespace split。
2. **Query 翻译**：`translate_query()` 把中文 query 翻译成英文后再检索，因为我们的语料（Recipe1M）是英文的。
3. **LLM 输出**：LLM 用原始中文 query 生成回答，输出中文。`_DEFAULT_SYSTEM_PROMPT` 明确指示 `Answer in the same language as the user's question.`"

### Q7: 为什么选 all-MiniLM-L6-v2 做嵌入模型，不用 text-embedding-3-small 或 bge-large？

"选 all-MiniLM-L6-v2 核心是 **轻量 + 够用**：

1. **384 维**：对比 text-embedding-3-small（1536 维），FAISS 索引体积小 4 倍，5000×384 的索引仅 ~8MB，纯内存操作。
2. **推理速度快**：CPU 上单条 ~5ms，GPU 上批量 ~1ms。bge-large 虽然精度更高但 1024 维，检索慢 3-5 倍。
3. **免 API 调用**：text-embedding-3-small 是 OpenAI 的 API 服务，每次检索都走网络，延迟不可控且有成本。本地部署的 all-MiniLM-L6-v2 毫秒级返回。
4. **对菜谱场景足够**：菜谱语义相对简单（菜名、食材、步骤），384 维的区分度已经够用。实测 Recall@10 在 85% 以上。"

### Q8: 为什么用 Redis 存会话，不用 MySQL / PostgreSQL？

"Redis 有几个天然优势：

1. **TTL 自动过期**：会话 86400s（24h）后自动过期，不需要写定时任务清理。用 MySQL 还要额外写 `DELETE WHERE last_active < NOW() - INTERVAL 1 DAY`。
2. **数据结构匹配**：会话天然是 List（轮次列表）+ Hash（元信息）+ String（摘要），Redis 的 List/Hash/String 直接对应，代码简洁。
3. **毫秒级读写**：内存操作，不管会话多长都是 O(1) 或 O(N) 的极低成本。MySQL 的 B+Tree 在频繁读写时有 IO 开销。
4. **单进程够用**：当前单机部署，Redis 单连接池支持数千 QPS，完全不是瓶颈。

当然也留了内存兜底——Redis 不可用时自动降级到 `_fallback_store` dict，保证不停机。"

### Q9: 为什么用 SSE 流式，不用 WebSocket？

"选择 SSE（Server-Sent Events）是因为：

1. **单向流就够了**：我们的场景只有服务器→客户端推送 token，没有客户端→服务器的双向实时通信需求。SSE 是 HTTP 原生的，简单可靠。
2. **兼容性好**：SSE 基于 HTTP，Nginx 不用额外配置就能代理。WebSocket 需要 Nginx 额外配置 `Upgrade` 头。
3. **实现简单**：FastAPI 的 `StreamingResponse` 配合异步生成器，几行代码就实现流式输出。
4. **自动重连**：浏览器原生 SSE 在断线后自动重连，WebSocket 需要手写重连逻辑。

不过如果未来要做实时语音交互或双向通信，WebSocket 会是更好的选择。"

### Q10: Embedding 索引用 IndexFlatIP（暴力搜索），数据量大了怎么办？

"当前 5000×384 的 FAISS 索引在全量暴力搜索下延迟 ~2ms，完全够用。但如果扩展到 50 万条，我会改成 **IVF+Flat** 或 **IVF+PQ**：

1. **IVF (Inverted File Index)**：用 K-means 聚类把向量分成 nlist 个簇，搜索时只搜索最近几个簇，复杂度从 O(N) 降到 O(N/nlist)。
2. **IVF+PQ (Product Quantization)**：进一步压缩向量，内存从 384×4 字节/向量降到 ~8 字节/向量，50 万条只用 ~40MB。
3. **分层检索**：先用 IVF 粗召回 Top-200，再用 BGE-Reranker 精排到 Top-10，保证精度不降。
4. **异步更新**：新增食谱时增量插入，定时全量重建索引，不停机。"

### Q11: PDF 解析为什么做双层引擎？

"因为我们遇到了 **精度和速度的权衡** 问题：

1. **PyMuPDF（快速模式）**：纯文本 PDF 解析极快（<1s），但遇到表格、多栏布局、图片夹带文字时，文字顺序乱掉，提取的内容不可用。
2. **magic-pdf / MinerU（增强模式）**：基于深度学习（ultralytics + doclayout_yolo）做版面分析，表格、图片、公式都能正确处理，但需要额外 2-3GB 显存，解析慢（~10s）。
3. **解决方案**：默认走 auto 模式——先尝试 magic-pdf 增强解析，如果环境不支持（缺 GPU / 缺模型）则静默降级到 PyMuPDF。用户通过 `pdf_mode` 参数控制。

这样既保证了复杂 PDF 的解析质量（走增强），又不让强依赖变成使用门槛（自动降级）。"

### Q12: 为什么用 sqlglot 做 SQL 校验，不用正则？

"正则校验 SQL 有几个致命问题：

1. **SQL 是上下文无关文法**：正则无法处理嵌套结构，`SELECT * FROM (SELECT * FROM recipes)` 正则很难正确解析。
2. **绕过风险**：攻击者可以用注释、字符串拼接等方式绕过正则。`SELECT/*comment*/DROP/*bypass*/TABLE`。
3. **AST 校验更安全**：sqlglot 把 SQL 解析成抽象语法树，能精确提取操作类型（`SELECT` vs `DROP`）、表名、列名。我们只允许 `SELECT` 语句和 recipes/nutrition/ingredients/steps 四个表，其他一概拦截。
4. **方言支持**：sqlglot 支持 MySQL、PostgreSQL、SQLite 等多种方言的解析，未来换数据库不用改校验逻辑。"

### Q13: 数据分块时步骤碎片化问题怎么解决的？

"最初按单条步骤切分 chunk，导致 LLM 拿到的可能是'Step 3: Bake for 20 minutes'这种碎片信息，看不到完整上下文。

**解决方案**：步骤不按单条切分，全部步骤合并为一个 chunk。

```python
steps_text = "\n".join(
    f"Step {s.step_number}: {s.content}" for s in sorted(recipe.steps, key=lambda x: x.step_number)
)
```

同时标题、食材、步骤分别存储为独立字段，检索时根据 intent 选择不同字段：营养查询搜食材字段，步骤问答搜步骤字段。"

### Q14: 如果并发量上来，本地 LLM 的线程锁怎么优化？

"当前本地 Qwen2.5-0.5B 是单例 + `asyncio.Lock` 串行执行，高并发时确实会排队。几个优化方向：

1. **短期方案 — 信号量限流**：用 `asyncio.Semaphore(3)` 允许 3 个并发推理，利用 GPU 的并行能力。Qwen2.5-0.5B 模型小，batch 推理效率高。
2. **中期方案 — vLLM 部署**：用 vLLM 替代原生 Transformers 推理，支持 continuous batching，多个请求自动拼 batch，吞吐量提升 5-10 倍。
3. **长期方案 — 缓存层**：对常见查询（'红烧肉做法'、'鸡蛋热量'）做 LLM 回答缓存，Redis 缓存命中直接返回，完全绕过 LLM。"

### Q15: FastAPI 重启后 Lucene/FAISS 索引需要重建吗？

"FAISS 索引是 **文件持久化** 的——构建完成后序列化为 `faiss_index.bin`，服务启动时 `faiss.read_index()` 加载到内存，耗时 ~50ms，不需要重建。

BM25 的词频统计也是持久化的——`pickle.dump` 存为 `bm25.pkl`，加载 ~200ms。

只有新增/修改了食谱数据才需要手动触发重建（`make rebuild-index`）。增量更新目前没做，50 万条以下全量重建 ~5 分钟，定时任务跑就行。"

### Q16: 为什么用 SQLite 做关系库，不用 PostgreSQL 或 MySQL？

"5000 条食谱数据用 SQLite 完全够用，且省去了数据库运维成本：

1. **零配置**：SQLite 是文件数据库，不需要安装、配置用户、管理端口。`sqlite3.connect('recipe.db')` 一行代码搞定。
2. **查询性能够用**：5000 条食谱、4 张表（recipes/nutrition/ingredients/steps）的复杂 JOIN 查询都在毫秒级返回。索引建好后，`WHERE cuisine_type='Italian' AND calories < 500` 这种过滤 <10ms。
3. **备份简单**：`cp recipe.db recipe.db.bak` 就是备份。PostgreSQL 还要 `pg_dump`。
4. **单机部署友好**：当前是单机部署，不需要数据库的网络连接和连接池管理。

**什么时候需要换 PostgreSQL**：当数据量超过 10 万条、需要高并发写入、或者需要多机部署时，SQLite 的并发写性能会成为瓶颈。届时切到 PostgreSQL 也很简单——SQLAlchemy 做了一层抽象，改一下 connection string 就行。"

### Q17: 为什么用 PyMuPDF 不用 pdfplumber 或 pdfminer？

"选型时对比了三个库：

| 库 | 纯文本速度 | 表格提取 | 多栏布局 | 依赖体积 |
|----|-----------|---------|---------|---------|
| **PyMuPDF (fitz)** | <1s ✅ | 支持 | 支持 | ~10MB ✅ |
| pdfplumber | ~3s | 支持 ✅ | 一般 | ~5MB |
| pdfminer.six | ~10s | 不支持 | 不支持 | ~2MB |

**PyMuPDF 胜出的关键**：速度最快（<1s），且内置了表格和布局分析功能。虽然 pdfplumber 的表格提取更精确，但 PyMuPDF + magic-pdf 的双层引擎组合在大多数场景下效果足够。

### Q18: 你们从 travel-agent-guide 移植了哪些设计？为什么？

"我从之前的 travel-agent-guide 项目移植了 5 个关键设计：

1. **Circuit Breaker（异步三态熔断器）**：保护 LLM API 调用不因连续失败而阻塞。3 次连续失败 → OPEN 熔断，30s 后 HALF_OPEN 探测恢复。**为什么移植**：API 调用失败时如果每次都等超时（~30s），用户体验极差。熔断后立即走本地回退，毫秒级响应。

2. **LongTermMemory（长效记忆）**：JSON 文件持久化，按 user_id 存储饮食偏好、过敏信息、收藏食谱等。**为什么移植**：原系统每次对话都是"陌生人"，不知道用户是否素食、对什么过敏。LongTermMemory 让系统能记住用户，提供个性化服务，且零外部依赖。

3. **ToolRegistry（工具注册中心）**：MCP 兼容的工具发现机制，支持 `register / has / get / list_tools / mcp_tool_catalog / discover_package / invoke`。**为什么移植**：Planner 需要动态调用工具，硬编码调用链扩展性差。ToolRegistry 让新工具只需写一个 `register_*` 函数即可自动注册。

4. **Planner Agent**：LLM 分解复杂请求为多步骤计划 → ToolRegistry 逐步执行 → LLM 汇总。**为什么移植**：用户可能问'先推荐低卡食谱，再查意大利面做法，然后做个对比'，原有单 Worker 架构处理不了多步骤请求。

5. **Reflection Agent**：LLM 驱动的深度质量检测（事实一致性/完整性/安全性/可操作性），带自动修订。**为什么移植**：Critic 是规则质检，只能检查模板化的合规问题（如免责声明）。Reflection 用 LLM 做语义级别的质量判断，能发现事实矛盾等深层问题。

### Q19: Router 的快慢车道 4 态合并策略具体怎么运作？

"这是从 travel-agent-guide 的 `_merge()` 逻辑移植来的。核心问题是：**规则通道和 Function Calling 结果冲突时听谁的？**

**4 态合并策略**：
```
① 规则置信度 ≥ 0.9 → fast_lane_only (直接走规则，跳过 FC，0ms)
② 规则 == FC intent → agree (取规则 confidence + 0.1 boost)
③ 规则 ≠ FC intent → conflict
   ├── 规则置信度更高 → conflict_prefer_rule
   └── FC 置信度更高 → conflict_prefer_fc
④ FC 完全失败 → fc_failed_fallback_to_rule
```

**为什么不做简单投票**：规则通道对高频关键词（'热量'、'低卡'）几乎 100% 准确，而 FC 可能因为 LLM 幻觉误判。反过来，复杂语义查询（'有个美国朋友来做客'）规则完全看不懂，必须靠 FC。4 态合并覆盖了所有场景，且每个结果携带 `merge_strategy` 字段，方便 debug。

### Q20: Planner Agent 和普通 Worker 有什么区别？

| 维度 | Planner Agent | 普通 Worker |
|------|-------------|------------|
| **触发条件** | 检测到规划关键词（'先…再…'、'plan'、'安排'）| 按 intent 路由 |
| **工作方式** | LLM 生成多步骤计划 → **ToolRegistry 逐步调用** | 一次性执行 |
| **工具调用** | 动态发现、灵活组合 | 固定 intent → 固定 Worker |
| **输出** | LLM 汇总各步骤结果 | 单步输出 |

**示例**：用户问'推荐 3 个低卡晚餐，再查第一个的详细做法'→ Planner 分解为：① `search_recipes('low calorie dinner', top_k=3)` ② 取第一个结果 → `search_recipes('recipe name', top_k=1)` ③ LLM 汇总两步结果。普通 Worker 只能处理其中一个步骤。

### Q21: Reflection Agent 和 Critic 的分工是什么？

```
Worker 输出 → Critic (规则质检, ~50ms)
               ├── 通过 → Reflection (LLM 深度质检, ~2s)
               │            ├── 通过 → save_memory
               │            └── 修订 → 替换 draft → save_memory
               └── 失败 → revision → Worker 重试
```

**Critic**：轻量规则检查（完整性、免责声明、有害内容），快速过滤明显问题，有重试循环。
**Reflection**：LLM 驱动的高成本深度检查，**不触发重试循环**（避免无限循环），而是自动修订后替换 draft。

**为什么加 Reflection**：Critic 只能检查'有没有免责声明'这种模板化问题，但发现不了'回答里说胡萝卜 50 卡，但检索结果是 41 卡'这种事实矛盾。Reflection 让 LLM 自己审自己的输出，语义级别的质量控制。

### Q22: LongTermMemory 的数据安全性怎么保证？

"LongTermMemory 使用 **JSON 文件持久化**，设计上做了几个安全考量：

1. **无外部依赖**：不依赖数据库，没有 SQL 注入风险，没有额外的网络攻击面。
2. **存储位置隔离**：数据文件存放在 `data/long_term_memory/` 目录下，不暴露在公网路径。
3. **每用户独立文件**：`{user_id}.json` 独立存储，不混放，方便隔离和清理。
4. **静默降级**：写入失败（磁盘满、权限问题）时静默跳过，不影响主流程。下次 `load()` 返回空记忆。
5. **无敏感信息设计**：存储的是饮食偏好、菜系偏好等非敏感数据，不存密码/token。

如果未来要存更敏感的信息，可以考虑加密存储或切换到专门的用户画像数据库。"

对于复杂 PDF（带表格、多栏、公式），我们还有 magic-pdf（MinerU）做增强解析——它基于深度学习的版面分析，能正确处理复杂布局。"

### Q18: 为什么用 asyncio.to_thread() 而不是直接开进程池或线程池？

"几个方案的对比：

1. **直接 `loop.run_in_executor()`**：功能相同，但 API 更底层——需要手动管理 `ThreadPoolExecutor` 实例。
2. **`asyncio.to_thread()`**：Python 3.9+ 的高级封装，内部也是调 `run_in_executor`，但自动使用默认的线程池，代码更简洁。
3. **`multiprocessing.Process`**：进程池适合 CPU 密集型任务，但 LLM 推理是 GPU 密集型，多进程拷贝显存上下文反而更慢。
4. **直接 `await model.generate()`**：如果模型本身支持异步（比如 vLLM 的 `async_generate`），可以避免线程切换。但 Transformers 的 pipeline 是同步的，只能用 to_thread。

选 `asyncio.to_thread()` 就是因为它 **最简单直接**——一行代码把同步阻塞调用抛到线程池，不阻塞事件循环。"

### Q19: 配置文件为什么用 pydantic-settings 而不是 yaml/json？

"pydantic-settings 有几个天然优势：

1. **类型安全**：`api_timeout: float = 10.0` 在加载时自动校验类型，YAML 的字符串类型要在运行时才 crash。
2. **环境变量覆盖**：`.env` 文件中的 `RECIPE_LLM_API_KEY=xxx` 自动映射到 `settings.llm_api_key`，不需要手写 `os.getenv()`。
3. **IDE 自动补全**：Pydantic BaseSettings 是 Python 类，调用 `settings.llm_api_key` 时有类型提示和自动补全，YAML 的 `config['llm']['api_key']` 没有。
4. **嵌套模型**：`class RedisSettings(BaseModel): host: str; port: int` → `settings.redis.host`，层级清晰。

YAML 只有在配置需要人工编辑且结构极其复杂（如 Kubernetes YAML）时才有优势，对于本项目 `pydantic-settings` 是更合适的选择。"

## 5. 技术亮点提炼

### 亮点 1：全链路容错设计

```
API LLM 失败 → 本地 LLM → 纯检索兜底 → 告知用户
Redis 不可用 → 进程内存兜底
PDF 增强失败 → PyMuPDF 降级
Worker 失败 → 预计算 Fallback 瞬间切换
```

### 亮点 2：113s → 12ms 的延迟优化

营养查询从 113 秒优化到 12 毫秒，优化接近 **10000 倍**。核心是识别出"每次走 LLM 翻译 SQL"是不必要的，用 5 个关键词 SQL 模板覆盖了 80% 以上的常见查询。

### 亮点 3：LLM 对话压缩 90%

后台异步压缩旧轮次，压缩率低至 9.7%，节省 90% Token。不阻塞主响应。

### 亮点 4：Function Calling 语义理解

规则通道处理明确关键词（0ms），Function Calling 处理复杂语义（~2s），两者互补。'有个美国朋友来做客，做什么给他吃'这种模糊表达也能正确识别。

### 亮点 5：LangGraph 重试循环

Critic 不通过 → revision 节点增计数器 → 回边到 worker 重新生成（携带 feedback）→ 最多 2 次 → 不通过则走兜底。这种回边机制在普通 DAG 中实现不了。

## 6. 项目难点与解决方案

| 难点 | 现象 | 根因 | 解决 |
|------|------|------|------|
| **显存爆炸** | 每个 Agent 独立加载模型，首个~43s，后续显存不够 | 无共享模型实例 | 全局单例 + `asyncio.Lock` |
| **事件循环阻塞** | FastAPI 接口卡死 | `model.generate()` 是同步阻塞 | `asyncio.to_thread()` 抛到线程池 |
| **113s 营养查询** | 低热量查询耗时 113s | 每次走 LLM 翻译 SQL → API 超时→本地模型 30s/次 × 3 轮重试 | 5 个关键词 SQL 模板 (0 LLM) |
| **双免责声明** | 回答出现两条免责声明 | NutritionSQL 和 Formatter 各加一条 | Formatter 统一添加，Critic 感知标志 |
| **Critic 重试循环** | 免责声明缺失触发反复重试，浪费 ~40s | `need_disclaimer=True` 时 Critic 仍检查 | 标志位跳过，由 Formatter 兜底 |
| **菜系不匹配** | 查'美国低热量'返回非美式菜 | Router 未提取菜系信息 | 规则通道 + FC 都提取 `cuisine_type` |
| **推荐质量差** | '推荐印度菜'只返回 2 道 | 检索 query 翻译不当 + top_k 小 | 菜系关键词构造 query + top_k 翻倍 |
| **模型加载慢** | 启动后首请求 ~43s | Transformers 从 HF 下载+加载 | lazy load + 全局单例 + HF 镜像 |
| **CLIP GPU 抢占** | 检索抢占了训练 GPU | 默认选 cuda:0 | `nvidia-smi` 解析空闲显存，≥3GB 才用 |
| **数据非结构化** | Recipe1M 原始数据混在一起，SQL 无法查询 | 纯文本无结构 | 自定义解析器拆分为标题/食材/步骤/营养字段 |
| **步骤碎片化** | LLM 拿到'Step 3: Bake 20min'碎片，无法生成完整回答 | 按单条步骤切 chunk | 全部步骤合并为一个 chunk，保持上下文完整 |
| **SQL 注入风险** | LLM 可能生成 DROP/INSERT/DELETE 危险语句 | NL→SQL 翻译不可控 | sqlglot AST 校验 + 仅允许 SELECT + 表名白名单 + 3s 超时熔断 |
| **API 超时体验差** | ModelScope API 超时 30s，用户空白等待 | 默认 timeout 30s，无快速失败 | 超时缩短到 10s + 重试 1 次 + 快速回退本地模型 (~1.5s) |
| **FC 输出格式错误** | Function Calling 偶发 JSON 缺括号/字段名错误 | LLM 生成不稳定 | try-catch 兜底 + 规则降级（置信度 0.7） |
| **State 类型不安全** | 某个节点返回 None，下游 AttributeError | TypedDict 无运行时校验 | 每个节点用 `state.get(field, default)` 兜底 |
| **中文检索效果差** | 中文查英文语料，BM25/FAISS 都匹配不到 | 语料英文，Query 中文 | translate_query() 翻译 + jieba 中文分词 + 双语检索 |
| **并发请求排队** | 多用户同时请求时本地 LLM 串行排队 | asyncio.Lock 全局锁 | 信号量限流 (Semaphore 3) / vLLM continuous batching / 缓存层 |
| **BGE-Reranker 加载慢** | 首次检索额外等待 ~10s | Reranker 模型加载耗时 | 全局单例 + lazy load，首调 ~10s 后续 ~500ms |

## 7. 英文版本

### 7.1 One-Liner

> "A multi-agent recipe QA system powered by LangGraph orchestration, featuring 8 collaborative agents for recipe recommendation, nutrition query, ingredient substitution, image search and PDF parsing, backed by 35B API LLM with automatic fallback to a local 0.5B model."

### 7.2 Core Architecture

"The system has three layers:

1. **API Layer** — FastAPI with REST and SSE streaming endpoints.
2. **Orchestration Layer** — LangGraph StateGraph with 10 nodes. Core flow: `init → load_memory → router → worker → critic → save_memory → formatter`.
3. **Agent Layer** — 8 specialized agents (Router, TextRAG, NutritionSQL, ImageSearch, PDFParse, Substitution, Critic, Formatter).

Key design principles:
- **Fault tolerance**: API LLM → local LLM → pure retrieval fallback. Never goes down.
- **Latency optimization**: Template-based SQL queries reduced latency from 113s to 12ms (10,000x improvement).
- **Memory management**: Redis persistence + token-aware sliding window + async LLM compression (90% token savings)."

### 7.3 Key Technical Decisions

| Decision | Rationale |
|----------|-----------|
| LangGraph over custom state machine | Directed graph enables back edges for retry loops |
| Function Calling over pure LLM | Intent + slot extraction in one call, structured output |
| RRF over weighted fusion | Rank-based, no score calibration needed |
| API-first + local fallback | 35B quality with 0.5B safety net |
| Global singletons | ~43s first load, ~1.5s subsequent calls |

### 7.4 Common Interview Q&A (English)

**Q: What's the most interesting technical challenge you solved?**

A: "Reducing nutrition query latency from 113 seconds to 12 milliseconds. The root cause was that every query went through LLM-based SQL translation, which timed out and fell back to the slow local model, then hit Critic retry loops. I added 5 regex-based SQL templates covering 80%+ of common patterns (low-calorie, high-protein, low-fat, etc.), eliminating LLM calls for most queries. This brought latency down to 12ms — a 10,000x improvement."

**Q: How do you handle multi-turn conversation?**

A: "We use Redis for persistence with a token-aware sliding window. The `get_context(max_tokens=2048)` method loads the most recent turns that fit within the budget. Older turns are asynchronously compressed by LLM into 1-3 sentence summaries, achieving 90% token reduction. Router receives both the summary and recent turns for context understanding."

**Q: Why use both BM25 and FAISS?**

A: "They complement each other. BM25 excels at exact keyword matching (e.g., 'braised pork belly'), while FAISS captures semantic similarity (e.g., 'something for an American guest'). We fuse them with RRF (Reciprocal Rank Fusion, K=60) which is score-agnostic, then re-rank with BGE-Reranker. This hybrid approach beats either single method."

**Q: Why LangGraph over LangChain Chains or custom state machines?**

A: "LangGraph's StateGraph offers three advantages. First, **directed graphs** naturally model multi-step orchestration — the flow from init to formatter maps directly to nodes and edges. Second, **conditional edges** enable intent-based dispatch — `route_by_intent` routes to worker or chitchat based on the intent field. Third, **back edges** support retry loops — Critic can reject and redirect back to worker for regeneration, which is impossible in a DAG. Custom state machines would work but lack type safety and require more boilerplate."

**Q: Why a local 0.5B model as fallback instead of a larger open-source model?**

A: "The 0.5B model fits in **~1.5GB VRAM** and can run alongside other components (FAISS, CLIP, Reranker) on a single RTX 5070 without OOM. A 7B model would require ~14GB VRAM, conflicting with other GPU workloads. The key insight is: the fallback only activates when the API is down, so it doesn't need to match the primary model's quality — it just needs to keep the service running with reasonable answers. The 0.5B model does exactly that."

**Q: How do you prevent SQL injection from LLM-generated queries?**

A: "We use a multi-layer defense. First, **sqlglot** parses the SQL into an AST — we extract the statement type and only allow `SELECT`. Second, a **table whitelist** restricts access to four tables: recipes, nutrition, ingredients, steps. Third, a **3-second timeout** circuit breaker prevents runaway queries. Finally, the query runs against a read-only SQLite database. This is much more robust than regex-based filtering, which can be bypassed with nested queries or comments."

**Q: What happens when Redis goes down?**

A: "The system auto-degrades to in-memory storage. `ConversationMemory` has a `_fallback_store` dict that mirrors Redis operations. When Redis connection fails, `_redis_available` is set to `False` and all operations switch to the fallback. The only downside is session data is lost on restart, but the service itself never goes down. This is tested and verified in production."

**Q: How would you scale from 5,000 to 500,000 recipes?**

A: "Three changes. First, **FAISS index**: switch from `IndexFlatIP` (brute force, O(N)) to `IVF+Flat` or `IVF+PQ` (inverted file, O(N/nlist)). Second, **BM25**: use Elasticsearch instead of in-memory Python implementation for distributed indexing and search. Third, **SQL**: migrate from SQLite to PostgreSQL for better concurrent read/write and connection pooling. The LangGraph orchestration layer and Agent architecture are already horizontally scalable — no changes needed there."

### 8.1 编排框架选型

| 选型 | 被比较对象 | 为什么选它 | 为什么不选另一个 |
|------|-----------|-----------|-----------------|

| **LangGraph** | 直接 if-else 调用 | 可视化编排；retry/fallback 统一管理 | 8 个 Agent 的 if-else 组合爆炸，不可维护 |

### 8.2 LLM 选型

| 选型 | 被比较对象 | 为什么选它 | 为什么不选另一个 |
|------|-----------|-----------|-----------------|

### 8.3 检索系统选型

| 选型 | 被比较对象 | 为什么选它 | 为什么不选另一个 |
|------|-----------|-----------|-----------------|
| **all-MiniLM-L6-v2** | text-embedding-3-small | 384 维轻量，FAISS 索引 ~8MB；本地 CPU/GPU 推理 | text-embedding-3-small 是 API，延迟 + 成本 + 网络依赖 |
| **all-MiniLM-L6-v2** | bge-large-zh | 384 维 vs 1024 维，检索快 3-5 倍；菜谱语义相对简单 | bge-large-zh 多语言能力更强，但 5000 条语料下精度差异 < 2% |
| **BM25 + FAISS** | 只用 BM25 / 只用 FAISS | 关键词精确匹配 + 语义相似度互补 | 单一检索方式有盲区：BM25 不懂语义、FAISS 不懂精确匹配 |
| **RRF (K=60)** | 加权平均融合 | 只看排名不看分数，无需调权重，对异构检索系统鲁棒 | 加权融合需要调权重，不同检索系统分数尺度不同，不稳定 |
| **BGE-reranker-v2-m3** | 只用向量检索 | CrossEncoder 精排比 BiEncoder 的向量检索精度高 5-10% | 延迟增加 ~200ms，但只在 Top-20 精排，开销可控 |

### 8.4 存储方案选型

| 选型 | 被比较对象 | 为什么选它 | 为什么不选另一个 |
|------|-----------|-----------|-----------------|
| **Redis** | MySQL / PostgreSQL | TTL 自动过期；List/Hash/String 天然匹配会话结构；毫秒级读写 | MySQL 读会话要 `SELECT * FROM turns` + 定时清理，复杂度高 |
| **SQLite** | MySQL / PostgreSQL | 5000 条单机够用；零配置；文件级备份 | 多机部署时需要切 PostgreSQL，但项目阶段 SQLite 更轻量 |
| **文件持久化 FAISS** | 每次都重建索引 | `faiss.read_index()` 加载 ~50ms；无需等待重建 | 修改数据后需手动触发 `make rebuild-index`，不支持实时增量 |

### 8.5 通信协议选型

| 选型 | 被比较对象 | 为什么选它 | 为什么不选另一个 |
|------|-----------|-----------|-----------------|
| **SSE (Server-Sent Events)** | WebSocket | 单向流够用；HTTP 原生；浏览器自动重连；Nginx 无需额外配置 | WebSocket 双向通信，本项目不需要；Nginx 要配 Upgrade 头 |
| **REST + SSE 双模式** | 只有 REST | 非流式请求走 REST 简单；流式请求 SSE 逐 token 输出 | 全 REST 的话长回答要等全部生成完，用户体验差 |

### 8.6 安全方案选型

| 选型 | 被比较对象 | 为什么选它 | 为什么不选另一个 |
|------|-----------|-----------|-----------------|
| **sqlglot AST 校验** | 正则表达式 | AST 级别解析嵌套结构；精确提取操作类型和表名 | 正则无法处理 `SELECT * FROM (SELECT ...)` 嵌套，且有绕过风险 |
| **3s 超时熔断** | 无限等待 | LLM 翻译 SQL 可能生成复杂查询跑死，3s 自动终止 | 无限等待可能导致资源泄漏 |
| **只读 SQLite + 表名白名单** | 只做 SQL 校验 | 即使校验有漏洞，数据库只读+限制表名，二次防御 | 单层校验不够安全，纵深防御更可靠 |

### 8.7 数据库选型

| 选型 | 被比较对象 | 为什么选它 | 为什么不选另一个 |
|------|-----------|-----------|-----------------|
| **SQLite** | PostgreSQL / MySQL | 零配置，一行代码连接；5000 条毫秒级查询；单文件备份 | 高并发写入场景需要 PostgreSQL，但当前单机部署 SQLite 更轻量 |
| **SQLite 只读模式** | 读写模式 | 禁止运行时写库，数据一致性有保障；防 SQL 注入补充防御 | 读写模式可能被恶意 SQL 利用修改数据 |

### 8.8 PDF 解析选型

| 选型 | 被比较对象 | 为什么选它 | 为什么不选另一个 |
|------|-----------|-----------|-----------------|
| **PyMuPDF (快速)** | pdfminer / pypdf2 | PyMuPDF 速度最快 (<1s)，提取质量在纯文本场景够用 | pdfminer 解析慢 10 倍 |
| **magic-pdf (增强)** | PyMuPDF 全文 | 基于版面分析，表格/多栏/公式正确还原 | PyMuPDF 在多栏布局中文字顺序错乱 |
| **auto 模式** | 只用一种 | 优先增强，失败静默降级，不因 PDF 模块影响整个服务 | 只用增强 → 环境缺 GPU 无法运行；只用快速 → 复杂 PDF 不可用 |

### 8.8 并发与性能选型

| 选型 | 被比较对象 | 为什么选它 | 为什么不选另一个 |
|------|-----------|-----------|-----------------|
| **asyncio.to_thread()** | loop.run_in_executor() | to_thread 是高级封装，用法更简洁 | run_in_executor 功能相同但 API 更底层 |
| **全局单例 + asyncio.Lock** | 每个请求加载一次模型 | 首调 ~43s 后续 ~1.5s；显存占用 1.5GB 固定 | 无共享 → OOM；每个请求加载 → ~43s/次 不可接受 |
| **Worker 先跑，Fallback 备胎** | asyncio.gather 并行 | Worker 成功立即返回，不等慢的 Fallback | gather 要等最慢的任务，Fallback ~20s 会拖慢全部 |

## 附录：推荐回答策略

### 回答节奏建议

1. **开头 30 秒**：一句话定义 + 核心数字（5000 条食谱、8 个 Agent、35B 模型）
2. **2 分钟阶段**：架构分层 + 核心流程 + 1-2 个亮点（推荐 113s→12ms 优化）
3. **深度追问**：按面试官兴趣深入某模块，准备好数据（压缩率 9.7%、显存 1.5GB 等）

### 回答原则

- **数据说话**：不只要说"优化了"，要说"从 113s 优化到 12ms，接近一万倍"
- **对比逻辑**：说"选 LangGraph 而不是手写状态机"比只说"用了 LangGraph"更有深度
- **承认不足**："幻觉检测目前还没完全做好"体现工程诚实和规划能力
- **业务关联**：每个技术选择要能说出业务收益（延迟降低、可用性提升、Token 节省）
